# 首頁廣告與 API 收費：設想

狀態：設想，尚未實作。金流、廣告網路與法規的細節都還沒有查證，下面的結論要在動工前逐項確認。

## 1. 範圍與原則

- **免費**：首頁、總經與市場資料、研究圖、主動提供的最新標的與技術研究、社群報告。
- **廣告**：只放在首頁。不放在研究內容、圖表標題或個股判斷段落中間，避免讀者把廣告當成研究結論。
- **收費**：只有 API 分頁。收費的是取得 API key 與用量，不是研究內容本身。
- 首頁文案要寫清楚「首頁有廣告、API 收費」，讓讀者事先知道。

## 2. 首頁廣告

做法有兩條路，建議先做第二條：

1. **廣告網路**（如 Google AdSense）：審核快，但金融內容常被限制或要求額外審核，且要處理 cookie 同意（PDPA、GDPR 適用的讀者）。
2. **直接贊助或自助版位**：版位固定、可控制內容與數量，初期收入較少，但不受廣告網路政策影響。

版位原則：
- 首屏之外的獨立區塊，例如圖表區之間或頁尾上方；不插入表格與圖表內部。
- 每頁最多兩個版位，加上「廣告」標示。
- 廣告內容不得是投資建議、個股推薦或與研究結論相關的內容；金融類廣告要另外審核。
- 登入的擁有者可以不看到廣告，或保留同一版位給自己的通知，視產品決定。

實作：版位由 `index.astro` 的獨立元件渲染；廣告腳本用 `defer` 載入，失敗時版位留白，不影響頁面其他部分。

## 3. API 收費與金流

### 3.1 帳號與登入

- 沿用既有 Keycloak realm `PeopleSystem`，為 API 入口新增一個 client（與 Birch 的 `birch-publisher-chatgpt` 分開，權限不共用）。
- 登入後進入「API 帳戶」頁：查看 key、用量、餘額與帳單。

### 3.2 金流方案比較

| 方案 | 適合 | 限制 |
|---|---|---|
| 綠界 ECPay / 藍新 NewebPay | 台幣收款、台灣讀者 | 定期定額方便，但不適合按用量逐筆計費，需另做點數 |
| Stripe | 國際讀者、按用量計費（metered billing） | 台灣需確認收款與稅務流程 |

建議：**先做點數制**（先儲值、每次呼叫扣點）。點數制可用綠界或藍新收款，不需要真正的按量計費，也比較好對帳。之後若國際讀者多，再加 Stripe。

### 3.3 流程

1. 使用者登入 → 建立 API 帳戶。
2. 儲值點數 → 金流 webhook 回傳成功 → 寫入 `api_credit_ledger`（只增不減的帳本，每筆附金流單號）。
3. 產生 API key → 只顯示一次 → 資料庫只存 SHA-256 雜湊（與 `MARKET_AGENT_KEY` 相同做法）。
4. 每次呼叫：驗證 key → 檢查點數與速率 → 扣點 → 記錄用量。
5. 退款、爭議與作廢都寫入帳本，不改舊紀錄。

## 4. API key 與計量

- 每個帳戶可有多把 key，各自有名稱、範圍（唯讀或特定端點）、建立與最後使用時間。
- key 可隨時撤銷；撤銷後立即失效。
- 速率限制：每把 key 每分鐘與每日上限，超過回傳 429。
- 用量記錄只存端點、時間、狀態碼與扣點數，不存請求內容。

## 5. 分期與測試（依 TDD 規則）

| 階段 | 內容 | 先寫的測試 |
|---|---|---|
| 0 | 文案與揭露（首頁、API 頁說明收費範圍） | 文案檢查（已在 `homeSeo.test.ts`） |
| 1 | 首頁廣告版位（靜態、可關閉） | 版位數量上限、廣告失敗時不影響其他區塊 |
| 2 | Keycloak client 與 API 帳戶頁 | 未登入不能看 key；key 只顯示一次 |
| 3 | 點數帳本與金流 webhook | 重複 webhook 不重複入帳；簽章不符一律拒絕 |
| 4 | key 驗證、扣點、速率限制 | 點數不足回 402；超過速率回 429；撤銷後立即失效 |

## 6. 風險（需先確認）

- **投顧法規**：如果收費內容包含個股「買進／減碼／等待」這類判斷，在台灣可能落入證券投資顧問業務，需要金管會登記。收費項目建議限定在**資料與工具**（API、資料整合），不收費給個股建議。這點必須先諮詢律師。
- **廣告政策**：金融內容在廣告網路上常受限，AdSense 規則要先查證，不要假設可以直接使用。
- **個資與 cookie**：廣告與分析追蹤要有同意機制；帳戶資料與金流資料分開保存，金流只存交易編號與狀態。
- **金流合規**：商店資料、退款與發票流程依所選金流的規定，上線前要測試沙箱環境。
