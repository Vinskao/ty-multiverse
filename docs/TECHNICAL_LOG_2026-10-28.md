# 從資料到決策：TY Multiverse 近期研究平台工程紀錄

最近幾天的開發重心，是讓研究流程裡的資料取得、整理、判讀與回查連成一條線。這不是單一功能更新：前端 Astro／TypeScript 負責呈現與互動，Python 後端負責資料採集、轉換與 API，投資組合與研究紀錄則保留來源、日期和可追溯線索。以下依 Git 於 2026-10-27 至 10-28 的變更整理。

## 總經資料：擴充國家範圍，也處理採集公平性

總經資料從美國與台灣擴充至日本、韓國等主要經濟體，增加失業率、消費者物價與貿易指標，前端則提供依國家及指標閱讀的分組方式。這類比較不能只把數字放在同一張圖：各來源的公布頻率、參考月份與單位不同，因此畫面要保留指標期間與來源差異。

韓國貿易資料也暴露了排程上的問題：若採集器總是先抓已存過的系列，新系列可能被既有資料占用的預算擠掉。修正後，優先處理尚未入庫的 FRED 系列，避免「支援了該指標」但資料一直空白。相應的測試涵蓋亞洲 CPI、採集預算與系列優先順序。

## 研究報告：從文章清單變成可查詢的證據來源

報告庫增加產業分類、搜尋與篩選，並將研究標籤整理成前端可共用的分類邏輯。SEC EDGAR 匯入會依申報文件切出報告段落，優先保留摘要、資金用途與管理層討論（MD&A），讓長篇申報更容易定位，而不是把整份文件當作一則無差別的摘要。

採集來源也往原文推進：TechNews 摘要中的連結會被解析成獨立文章，保存文章全文作為研究報告；Telegram 頻道蒐集新增 TechNews 與 Bloomberg 來源。報告、原文與依報告整理出的主張是不同資料層，後續研究可以回到原文檢查，不必把摘要或模型整理誤當成來源本身。

公開 API 參考頁則改為讀取後端路由上的公開標記與規格，減少文件清單和實際端點各自維護而逐漸不一致的風險。公開端點與需要登入的操作仍以後端權限為準；前端說明頁不取代 API 的授權檢查。

## Binance：把行情、資產與成本分開處理

市場資料服務新增 Binance 現貨行情與日線 K 線，投資組合畫面也將唯讀帳戶餘額納入資產區域分布。這兩種資料用途不同：公開行情用於觀察價格，帳戶餘額用於呈現持倉；若帳戶資料無法取得，不應以行情資料猜出持倉。

持倉損益依可識別的成交與轉換紀錄建立成本基礎。當成本資料不足時，畫面只標示已有成本依據的損益，並在提示中說明成本狀態，不把未知成本包裝成精確報酬。相關改動包含成本計算、資產合併及區域分布測試。

## AI 分析：保留可驗證的時間線

每日 AI 分析修訂新增 OpenTimestamps 時戳紀錄，並把時戳與分析修訂關聯。它提供的是事後驗證內容在某個時間點已存在的證據，不代表分析內容正確，也不能替代來源查核。測試使用固定二進位 fixture，避免換行轉換讓時戳驗證失效。

## 工程取捨與驗證方式

這批變更的共同原則是：保留資料的來源和時間語意、把不同用途的資料分開，以及讓分類與 API 規格盡量由可維護的結構產生。前端工作以 TypeScript 測試鎖定分類、搜尋、圖表與投資組合呈現；後端則針對資料解析、採集預算、成本計算、API 權限與時戳流程補上測試與 fixture。

Git 依據包括：`ty-multiverse-frontend` 的 `3cc18c6`（日本與韓國總經）、`c0a1c8c`／`3234061`（報告搜尋與分類）、`9752938`／`8f6c7c5`／`dd5b47d`（Binance 投資組合與行情）；`maya-sawa` 的 `7877c35`／`7c504c1`（韓國貿易採集與亞洲 CPI）、`7e2ca9c`（SEC 分段匯入）、`cbcdd02`／`cfca154`（TechNews 與 Bloomberg 採集）、`885e619`（OpenTimestamps）。這些是程式碼與測試的交付紀錄，不代表所有資料來源都已達到即時、完整或無缺漏。

## 接下來要觀察的限制

- 宏觀指標的發布日與參考期不同，來源修訂也可能改變既有數值；資料新鮮度仍須逐系列檢查。
- 新聞全文擷取受來源網站結構、可讀性與連線限制影響，抓取成功不等於內容已完成研究判讀。
- Binance 成本僅能依可配對的成交與轉換資料計算，缺少歷史紀錄時仍需清楚顯示未知。
- OpenTimestamps 可協助驗證時間順序，不能證明資料真實、模型推論有效或投資結論正確。

這輪工程的目標，是讓個人研究流程更容易回答三個問題：資料從哪裡來、判斷根據什麼、日後如何確認當時看到了什麼。系統可以協助整理與留痕，最後的投資決策仍由使用者負責。
